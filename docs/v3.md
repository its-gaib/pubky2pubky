# pubky2pubky protocol v3

Protocol v3 makes Pubky public storage the directory for native iroh endpoints. It removes the
custom WebSocket consent rendezvous from the connection path. This document describes the v3
security and operational model; [protocol.md](protocol.md) remains the normative v2 specification.
V2 and v3 use different storage paths, signing domains, ALPN values, and commands. An
implementation must never reinterpret one version as the other or silently downgrade after a v3
failure.

## Model

```text
target Pubky ID
    -> PKARR resolves the target's homeserver
    -> homeserver returns the target's root-signed device directory
    -> homeserver returns a short-lived locator signed by an authorized device
    -> caller verifies every signature, binding, lifetime, and sequence
    -> caller constructs an iroh EndpointAddr from the certified endpoint ID and trusted relay
    -> iroh establishes authenticated QUIC through the relay
    -> iroh attempts direct UDP hole punching and migrates when the network permits it
    -> a bounded signed hello binds both Pubky identities and device certificates to QUIC
    -> the receiver accepts or rejects that authenticated request
    -> only acceptance sends a signed ack and exposes the Peer to application payload handlers
```

The homeserver is a signed directory, not a signaling server or packet relay. PKARR and the
homeserver may suppress or replay data, but they cannot forge a valid device authorization or
locator. Iroh supplies reachability, NAT traversal, authenticated QUIC, and encrypted relay
fallback. A homeserver fork is not required.

Application payloads are end-to-end encrypted by iroh's QUIC/TLS 1.3 connection on both the relay
path and after direct migration. The signed Pubky root-to-device chain binds the expected iroh
endpoint ID, and QUIC proves possession of that endpoint's secret key. The homeserver and relay
never receive application plaintext, and v3 has no plaintext transport fallback. They still see
metadata described below. This transport guarantee also does not encrypt local credential files,
chat history, terminal arguments, logs, or application storage; those are separate at-rest and
endpoint-security responsibilities.

The reference v3 client never sends QUIC 0-RTT and sets `max_tls_tickets(0)` to disable outbound
session reuse. It rejects an accepted stream when iroh reports it as 0-RTT. Iroh 1.1 does not expose
a server switch that can prevent every hostile custom peer from sending encrypted, replayable early
handshake input, so the signed Hello replay cache remains mandatory. No early input is exposed to
application payload handlers: signed Hello/Ack authentication and explicit receiver acceptance
complete before a `Peer` is returned. The transport can still buffer bounded encrypted input from a
hostile peer before that decision. Do not add a 0-RTT fast path without a new replay and consent
analysis.
Proving that hostile inbound 0-RTT is impossible requires an upstream iroh server option that sets
the rustls maximum early-data size to zero; iroh 1.1 does not expose that switch.

V3 provides live connections only. It has no mailbox, queue, store-and-forward behavior, delivery
receipt, or guarantee that a published device is online.

## Identity and key lifecycle

Three roles stay separate:

- The Pubky root key signs a bounded device authorization. Keep it offline or behind a Pubky Ring
  signer. It is not an iroh endpoint key and must never be loaded by the long-running listener.
- The delegated device signing key signs short-lived locator updates. It is an online credential
  and can refresh reachability without the Pubky root.
- The dedicated iroh key authenticates QUIC. Its endpoint ID is bound by the root-signed device
  authorization; compromising it does not grant Pubky root authority.

Issue each device independently, use the shortest practical authorization lifetime, and remove
retired devices from the next root-signed directory. A removed or stolen device remains usable
until clients observe the newer directory and reject the old sequence, or until its authorization
and locator expire. Root compromise is identity compromise and requires migration to a new Pubky
identity.

Offline issuance and online publication are intentionally different operations:

1. An offline root signer creates or updates the device directory.
2. The device starts its iroh endpoint and signs a fresh locator with its delegated signing key.
3. A process holding an already-authorized `PubkySession` publishes the directory or locator.
4. The listener refreshes its signed locator when the relay changes or before expiry; an
   application-specific publisher transports those bytes to the authenticated session boundary.

The reference file-backed CLI may create a short-lived Pubky session in a separate publisher
process for development. Production applications should pass an already-authorized session from
their account layer. Do not copy a recovery phrase or root-secret file into the listener service.

## Directory and locator rules

Store v3 records only below the v3 namespace. A directory enumerates root-authorized devices;
each device publishes its own locator file so concurrent devices do not overwrite one another.
The exact paths are:

```text
/pub/pubky2pubky/v3/directory.json
/pub/pubky2pubky/v3/locators/<canonical-control-signing-key>.json
```

V3 uses the fixed QUIC ALPN `pubky2pubky/iroh/v3`. Its signature domains all begin with
`pubky2pubky/` and end in `/v3` (`device-certificate`, `device-directory`, `iroh-locator`,
`iroh-locator-digest`, `hello`, `hello-digest`, and `ack`). No v3 verifier accepts the historical
`hole-punchky` v2 namespace, domains, credentials, or ALPN.

A locator contains only what the caller needs to construct an iroh address:

- the Pubky identity and authorized device ID;
- the certified iroh endpoint ID;
- one or more home-relay URLs;
- the fixed v3 QUIC ALPN (the separate application label is carried in the signed Hello);
- issuance and expiry timestamps;
- a monotonically increasing per-device sequence;
- a device signature covering every field.

Do not publish direct socket addresses. Once the relay path connects, iroh exchanges current
candidates and attempts direct migration itself. Omitting direct addresses from public storage
reduces stale data and avoids disclosing them to every homeserver reader, but it does not prevent
the eventual peer from learning addresses during direct-path negotiation.

Locators must be short-lived. Publishers must increase the per-device sequence durably and never
reset it after process restart. Resolvers remember the greatest accepted directory and locator
sequence for each identity/device and reject rollback, even when an older record still has a valid
signature and timestamp. Clock validity is necessary but is not a replacement for rollback state.

Directory generation is offline operator state with the same no-rollback rule. Record and back up
the next generation alongside the offline root workflow before publishing. If that state is lost,
do not guess or restart at one: recover the last published generation from a trusted backup and
independent observations. If no trustworthy floor exists, migrating to a new Pubky identity is the
only unambiguous recovery. Losing a device's publisher-sequence state requires retiring that
certificate and issuing a new control key; reusing the old key with sequence one invites rollback.

## Public contact and loss of pre-consent privacy

V2 withheld the receiver's iroh address and blocked peer QUIC until a receiver explicitly accepted
a knock. V3 deliberately removes that *pre-network* gate. Anyone who can read a Pubky identity's public records
can learn its stable device/endpoint identifiers and chosen relay, attempt an iroh connection, and
probe whether a listener appears online. During iroh candidate exchange or direct migration, an
untrusted caller may also learn public, carrier, VPN, and local-interface address candidates before
the application accepts a message.

The receiver still authenticates the signed Hello and makes an application-level accept/reject
decision before sending the signed Ack or exposing a `Peer` to application payload handlers. The
transport can buffer bounded encrypted input from an untrusted peer before that decision, but the
application neither sees nor processes it. That preserves message and application authorization,
but the QUIC contact and possible address disclosure have already happened.

This matters most when a public or pseudonymous Pubky must not be correlated with a physical
network, when merely being online is sensitive, or when unsolicited connection attempts create a
meaningful harassment or denial-of-service risk. QUIC encryption still protects application data,
and the signed hello still prevents identity impersonation, but neither hides network metadata.

The native API therefore requires applications to explicitly acknowledge public-contact address
exposure before constructing a direct-capable endpoint. The reference v3 API currently exposes
only direct-with-relay-fallback, not a peer-address-hiding relay-only policy. A future relay-only
mode could prevent direct peer address exchange at the cost of latency, relay bandwidth, and
revealing traffic metadata to the relay. Until then, privacy-sensitive identities should not
publish v3 records. If accept-before-contact is a hard requirement, use v2 or a future
privacy-preserving invitation service; v3 cannot provide that property while keeping a generally
readable locator.

## Relay trust and egress policy

A target-signed relay URL authenticates the target's preference; it does not make that URL safe for
the caller. Blindly dialing relay URLs from public records turns discovery into attacker-controlled
network egress and can reach internal services through DNS or redirects.

Every client must enforce a local trusted-relay allowlist before network access. Match normalized
HTTPS origins, reject credentials, fragments, unexpected ports, local/link-local/private targets,
redirects outside the allowlist, and DNS answers that violate the configured policy. Development
HTTP exceptions must be explicit and loopback-only. A locator with no permitted relay fails closed;
the client must not fall back to an untrusted URL, global discovery, v2, or a direct address supplied
outside the signed v3 record.

The relay sees endpoint IDs, source addresses, timing, destinations using that relay, byte volume,
and encrypted packet sizes. It cannot impersonate a certified endpoint or decrypt authenticated
QUIC application bytes. Multiple permitted relays improve availability but increase the set of
operators that can observe this metadata.

## Connection authentication

The certified iroh endpoint ID must equal the endpoint ID in the locator, and the completed QUIC
connection's remote ID must equal both. The first bounded stream exchange then proves the device
signing key and binds:

- protocol version and fixed v3 ALPN/application label;
- caller and receiver Pubky identities;
- caller and receiver device IDs and current authorizations;
- caller and receiver iroh endpoint IDs;
- fresh nonces and a bounded validity window.

Reject unknown devices, expired authorizations, stale locators, identity or endpoint substitution,
bad signatures, oversized frames, replayed nonces, and wrong ALPN before showing the request for
acceptance. Send the Ack and expose the `Peer` to application payload handlers only after that
decision; bounded encrypted transport input may already be buffered. Authentication proves control
of keys; it does not grant contact authorization. Applications still need block lists, allowlists,
rate limits, and their own message policy.

## Native and browser behavior

Native iroh endpoints can use relay fallback and direct UDP hole punching. A successful connection
may remain relayed; symmetric NAT, carrier policy, firewalls, captive portals, and UDP blocking make
direct connectivity impossible in some networks.

Iroh's browser/Wasm transport is currently relay-only because browsers cannot expose the raw UDP
socket behavior used by native iroh NAT traversal. V3 can authenticate and carry browser traffic
through a compatible relay, but it must not report that as a direct browser-to-browser path.
Direct browser-to-browser transport requires an upstream iroh browser transport, WebRTC as an
explicit separate transport, or a native companion. A UI must report the observed path honestly.

The end-to-end guarantee holds only when the authenticated iroh QUIC connection terminates in each
user's browser or native endpoint. A WebSocket or HTTP bridge that terminates QUIC on a server can
read the chat payload and is not an E2E v3 transport; do not use such a bridge for message data.

## Migration from v2

V3 is additive. During migration, an identity may publish both versioned record sets and an
application may expose an explicit user choice, but a v3 attempt never automatically falls back to
v2. In particular, failure of freshness, sequence, relay policy, or authentication is not a signal
to retry a weaker protocol.

Reissue v3-compatible device authorization and initialize durable sequence state. Publish the v3
directory and one fresh locator per online device. Validate resolution and relay fallback before
retiring v2. Removing the v2 records removes its rendezvous discovery but does not revoke already
issued v2 credentials.

## Required evidence before production use

Do not infer completion from unit tests alone. A release candidate must demonstrate:

- two signed-up Pubky test identities where the caller starts with only the receiver's Pubky ID;
- PKARR/homeserver resolution, signature verification, and exact trusted-relay enforcement;
- a relayed authenticated message and exact echo;
- direct migration on two independent NATed native networks, with packet/path evidence;
- encrypted relay fallback when UDP is blocked, using the internal forced-relay test path;
- rejection of tampered, expired, cross-identity, wrong-endpoint, and rolled-back records;
- multiple devices without lost updates and durable sequence continuity across restarts;
- bounded handling of unsolicited QUIC connections and replayed/oversized hellos;
- an honest relay-only result for browser/Wasm clients.

For both relayed and direct cases, verify the remote QUIC endpoint ID against the Pubky-certified
ID and capture enough relay/homeserver telemetry to show that neither service receives the
synthetic plaintext. Do not treat TLS to the homeserver or relay as the E2E proof: the evidence is
the single authenticated iroh QUIC connection carrying the same stream across path migration.

Until those gates pass, describe v3 as implemented or experimental—not production-proven.
