# Pubky2Pubky protocol v4

V4 maps a Pubky identity to an authenticated iroh endpoint without giving the web application a
Pubky root key. It uses the standard Pubky 0.11 Grant chain and stores only public discovery and
short-lived authority evidence on the user's homeserver. Chat bodies travel only inside the iroh
QUIC connection.

V4 is wire-incompatible with v3. Implementations must use the v4 paths and ALPN and must not
silently downgrade.

```text
Pubky ID
  -> PKARR homeserver resolution
  -> /pub/pubky2pubky/v4/devices/*.json
  -> authenticated iroh QUIC (relay-only in a browser; direct-capable natively)
  -> mutual short-lived homeserver write proofs after recipient acceptance
  -> application messages
```

## Identity chain

The public authentication chain has four keys with separate jobs:

1. The Pubky root key signs a standard `pubky-grant` JWS. It remains in Pubky Ring and is never
   entered into the chat application.
2. The Grant `cnf` key proves possession for the Grant and signs one purpose-specific v4 device
   certificate. In a browser this is a non-extractable WebCrypto Ed25519 key.
3. The device control key signs locators, handshakes, and currentness proofs.
4. The independent iroh endpoint key authenticates the QUIC connection and its end-to-end
   encryption.

The Grant must contain write authority covering `/pub/pubky2pubky/`. The device certificate binds
the exact Grant digest and id, identity, client id, `cnf` key, control key, iroh endpoint id, device
name, and a bounded validity interval. Equal keys across these roles are rejected.

## Homeserver data

An online device publishes one self-contained JSON record below:

```text
/pub/pubky2pubky/v4/devices/<hash-of-grant-cnf-and-control-keys>.json
```

The record contains:

- the root-signed Grant JWS;
- the Grant-`cnf`-signed device certificate; and
- a control-key-signed, short-lived locator containing the identity, record digests, iroh endpoint
  id, one to four relay URLs, fixed v4 ALPN, random instance nonce, monotonic sequence, and validity
  interval.

It contains no recovery phrase, root secret, Grant `cnf` secret, control secret, iroh secret, direct
IP address, relay credential, contact list, conversation identifier, peer Pubky, or chat body.

After the recipient accepts a request, each peer briefly publishes one proof below:

```text
/pub/pubky2pubky/v4/currentness/<hash-of-role-challenge-and-transcript-digests>.json
```

The proof contains the signer's role, a fresh shared challenge, digests of the exact Hello, Grant,
device record, and locator, a validity window of at most 30 seconds, and a device-control
signature. The peer's Pubky is deliberately absent. Each peer fetches and verifies the other's
exact proof, and each writer deletes its own proof on a best-effort basis after the exchange.
Expiry remains the security boundary if deletion fails.

The proof demonstrates that the endpoint-key holder also had live identity-level write authority
for the Pubky namespace during acceptance. Public storage does not reveal which authorized Grant
performed a write, so this is not an exact-Grant revocation oracle and must not be described as
one.

## Connection sequence

1. A user chooses a recipient Pubky. This authorizes outbound PKARR/homeserver discovery for that
   identity.
2. The initiator lists a bounded number of v4 device records, verifies every signature and
   lifetime, and ignores any relay origin outside its locally configured exact allowlist.
3. The initiator contacts one advertised iroh endpoint and sends a signed, bounded Hello. The Hello
   embeds the initiator's complete record and binds the exact recipient record, application, ALPN,
   endpoint ids, and fresh nonce.
4. The recipient authenticates the completed QUIC handshake and verifies the Hello entirely
   offline. It performs no sender-selected PKARR, DNS, or homeserver request before showing the
   inbound request.
5. Rejecting or dropping the request closes the connection. Accepting it authorizes the following
   live-authority checks; it does not retroactively hide the already observed network metadata.
6. The responder publishes its currentness proof and sends a signed Ack carrying a fresh challenge.
7. The initiator verifies the Ack, publishes its proof, fetches and verifies the responder proof,
   and signals proof readiness over the authenticated QUIC transcript.
8. The responder fetches and verifies the initiator proof, atomically commits the authenticated
   record/sequence floor, and confirms over QUIC.
9. The initiator receives confirmation and atomically commits its corresponding floor. Only then
   may either side expose an application `Peer` or exchange chat messages.

All handshake and control frames have fixed size limits and deadlines. Replayed Hello nonces,
expired records, lower locator sequences, or different records at an already accepted sequence are
rejected. There is no plaintext or non-QUIC fallback and no automatic protocol downgrade.

## Encryption and metadata

Iroh QUIC authenticates the certified endpoint keys and encrypts application bytes end to end with
TLS 1.3. A relay forwards ciphertext; it cannot decrypt chat bodies. Pubky homeservers never
receive chat bodies.

That does not make the transport metadata-free. A configured relay can observe endpoint ids,
client IP addresses, connection timing, duration, and traffic shape. The recipient's relay and
endpoint receive an encrypted QUIC connection before the recipient makes the application-level
accept/reject decision. V4 therefore provides consent before live Pubky checks and application
messages, not consent before all network contact.

Browser/Wasm clients are relay-only because browsers do not expose the UDP facilities iroh uses
for direct path discovery. Native clients may use relay-assisted UDP hole punching and migrate the
same encrypted QUIC connection to a direct path. Direct peers can learn one another's network
addresses.

## Browser key and state rules

- Request a separate least-privilege Grant for `/pub/pubky2pubky/:rw` through Pubky Ring.
- Store the Grant `cnf` private key only as a non-extractable WebCrypto key handle in IndexedDB.
- Persist only delegated Grant restore metadata; never export or persist the `cnf` secret.
- Encrypt serialized control and iroh device secrets under a non-extractable AES-256-GCM key with
  account- and version-bound associated data.
- Allocate locator sequences and commit accepted remote sequence/digest floors in IndexedDB
  transactions. If the protected key or publisher state is lost, rotate the device instead of
  reusing its old control key at sequence one.
- Permit only one online leader tab for an origin/account. A second tab must fail explicitly rather
  than race locator publication.
- Store chat history separately in the application. Deleting browser storage deletes local history
  and device state; it cannot recall messages already received by a peer.
